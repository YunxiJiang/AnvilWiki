## 2. 架构

### 2.1 整体形态

新增一个 `Comments.astro` 组件,挂在 `ArticlePage.astro` 正文 + tags 之后、InContentAd 之前。组件读取 env 变量,**空值时 `return null` 不渲染任何东西**(与现有广告组件同一模式)。启用时渲染一个 `loading="lazy"` 的 Giscus iframe,并用 ~20 行 vanilla JS 让它跟随站点暗色模式。

### 2.2 三层架构落点(严格遵守 AGENTS.md)

```
框架层 (不改动)
└── src/components/article/Comments.astro    🆕 新组件,纯通用逻辑,零游戏字符串

配置层 (改一处)
├── .env.example                              🆕 加 Giscus 配置段(空值)
└── src/locales/{en,ja}.json                  🆕 加 shared.commentsHeading 文案

内容层 (不动)
└── MDX 文件不碰(mapping = pathname,无需 frontmatter 字段)
```

**关键**:Comments 组件本身不持有任何游戏专属配置 —— repo / categoryId 这些都从 env 读,组件只是通用的 Giscus 渲染器。换皮用户改 `.env` 即可,不动框架代码。

### 2.3 与现有模式的对照

| 现有模式 | 评论组件复用 |
|---|---|
| `InContentAd.astro`:env 空值 → `return null` | Comments 完全相同 |
| 主题切换器:vanilla JS toggle `.dark` | Comments 用 postMessage 把 `.dark` 状态同步给 iframe |
| i18n:`shared.*` 文案在 JSON | `shared.commentsHeading` 同源 |
| ArticlePage 已是文章页唯一组装点 | 在它里面加一行 `<Comments ... />` 即可 |

## 3. 组件内部结构

### 3.1 Props 与 env 契约

```astro
---
// src/components/article/Comments.astro
interface Props {
  locale: Locale;          // 跟随页面 locale,决定 Giscus UI 语言
  pathname: string;        // 当前文章路径,作为 discussion mapping key
}
---
```

组件不接收任何 Giscus 业务配置(repo / categoryId / mapping 等),全部从 `import.meta.env` 读。这样 `ArticlePage` 调用处保持干净:`<Comments locale={locale} pathname={Astro.url.pathname} />`。

### 3.2 env 变量设计(5 个业务字段空值默认 + 1 个 mapping 带默认值)

```bash
# .env.example 新增段
# ─── Giscus comments (optional) ──────────────────────────────────────
# Leave empty to disable comments (default). Fill all 5 to enable.
# Get these from https://giscus.app after configuring your repo:
PUBLIC_GISCUS_REPO=                   # e.g. "PNGTRID/anvilwiki-comments"
PUBLIC_GISCUS_REPO_ID=
PUBLIC_GISCUS_CATEGORY=               # e.g. "Announcements"
PUBLIC_GISCUS_CATEGORY_ID=
PUBLIC_GISCUS_MAPPING=pathname        # 固定值,文档说明不改
```

**为什么 `mapping` 也做成 env 而非硬编码**:虽然本次设计确定 `pathname`,但留作 env 字段(带默认值 `pathname`)可以让进阶用户不改动组件代码就切到 `title` / `og:title` 等其他映射。代价是 6 行文档。考虑到这是开源模板,「不碰框架代码就能改」的价值大于少一个 env 字段。

### 3.3 启用判定逻辑

```astro
const { locale, pathname } = Astro.props;
const env = import.meta.env as Record<string, string | undefined>;
const repo = env.PUBLIC_GISCUS_REPO;
const repoId = env.PUBLIC_GISCUS_REPO_ID;
const category = env.PUBLIC_GISCUS_CATEGORY;
const categoryId = env.PUBLIC_GISCUS_CATEGORY_ID;
const mapping = env.PUBLIC_GISCUS_MAPPING || 'pathname';

// 4 个必填字段任一为空 → 整个组件 return null(与 InContentAd 同模式)
const enabled = Boolean(repo && repoId && category && categoryId);
---
{!enabled && null}
{enabled && ( ... 实际渲染 ... )}
```

**判定规则**:4 个业务字段(repo/repoId/category/categoryId)任一为空 → 不启用。`mapping` 有默认值 `pathname`,不算启用条件。这样用户「填一半」时不会渲染出一个坏掉的 iframe。

### 3.4 locale → Giscus 语言映射

Giscus 的 `data-lang` 接受 `en` / `ja` 等短码,与站点 locale 值直接对应。组件内维护一张白名单常量:

```ts
// 仅列出站点实际支持的 locale(en/ja),其余 fallback 到 en
const GISCUS_LANG: Record<string, string> = { en: 'en', ja: 'ja' };
const lang = GISCUS_LANG[locale] ?? 'en';
```

**为什么显式映射而不直接传 `locale`**:Giscus 的语言代码与 BCP-47 不完全一致,用白名单显式映射是防御性的。当前只两个 locale,成本极低。

### 3.5 渲染输出:静态 iframe(非官方 `<script>` 注入)

**实现选择**:用 Giscus 官方推荐的 `<script>` 注入方式,还是直接静态写 `<iframe>`?

- **`<script>` 注入**(官方默认):Giscus 给一段 `<script src="https://giscus.app/widget.js">`,它运行时创建 iframe。问题:多一个外部 JS 请求,Lighthouse 把它计入 render-blocking 附近指标。
- **静态 `<iframe loading="lazy">`**(本设计采用):直接在 HTML 里写好 iframe 标签,把 Giscus 的所有 `data-*` 参数转成 iframe 的 query string。浏览器原生 lazy,无需额外 JS 就能延迟到接近视口才加载。

**选静态 iframe 的理由**:Lighthouse 友好(无 render-blocking script)+ 可控(loading=lazy 是 HTML 属性)。代价是 query string 要自己拼(实现时按 Giscus 文档的 [Using iframe](https://github.com/giscus/giscus/blob/main/ADVANCED.md#using-iframe) 段落组装)。

### 3.6 暗色模式同步(~20 行 vanilla JS)

Giscus 的主题是它自己的 `data-theme` 参数,不自动读站点 `.dark` class。用 Giscus 官方的 `postMessage` 协议切主题(不是销毁重建 iframe):

```js
function syncTheme() {
  const theme = document.documentElement.classList.contains('dark')
    ? 'dark_dimmed'      // Giscus 内置暗色主题
    : 'light';            // Giscus 内置亮色主题
  const iframe = document.querySelector('iframe.giscus-frame');
  iframe?.contentWindow?.postMessage(
    { giscus: { setConfig: { theme } } }, 'https://giscus.app'
  );
}
// 1. 初始纠正 + 持续监听
document.addEventListener('DOMContentLoaded', syncTheme);
new MutationObserver(syncTheme).observe(
  document.documentElement,
  { attributes: true, attributeFilter: ['class'] }
);
// 2. iframe 加载完成时再同步一次(覆盖加载期间的主题切换)
document.querySelector('iframe.giscus-frame')?.addEventListener('load', syncTheme);
```

**关键点**:
1. 监听 `<html>` 的 `class` 属性(站点现有主题切换器 toggle 的就是 `.dark` on `<html>`)
2. 主题选 `dark_dimmed`(对眼睛友好,与多数 wiki 站暗色风格匹配)
3. `is:inline` 让 Astro 不处理这段脚本(避免被 bundle 延迟)

**为什么主题不做成可选**:Giscus 有十几个内置主题,但 `light` + `dark_dimmed` 是最安全的默认组合。自定义主题 CSS 需换皮用户自己托管文件,ROI 太低,本次不做。

## 4. ArticlePage 集成与边界情况

### 4.1 ArticlePage.astro 改动(极小)

只动两处:import 一行 + 渲染一行。

```astro
---
import Comments from '~/components/article/Comments.astro';
import InContentAd from '~/components/ads/InContentAd.astro';
...
---

{/* Tags 区块结束之后,InContentAd 之前插入 */}

{/* Comments — env 空值时组件内部 return null,这里不需要条件判断 */}
<Comments locale={locale} pathname={Astro.url.pathname} />

{/* In-content ad before related articles */}
<InContentAd type="banner-728x90" />
```

**为什么调用处不写条件判断**:`Comments` 内部已做 `enabled` 判定,调用处再包一层会把 env 读取逻辑泄漏到 ArticlePage,破坏「Comments 是自包含的黑盒」边界。与 `InContentAd` 调用风格完全一致。

### 4.2 pathname 在不同 locale 下的值(mapping 正确性验证)

mapping = pathname 意味着 Giscus 用 URL 路径区分讨论帖。不同 locale 的同一篇文章会创建不同的 Discussion —— 这是 **期望行为**(en/ja 评论区独立)。

| 页面 | `Astro.url.pathname` | Giscus Discussion |
|---|---|---|
| `/bosses/gelum`(英文) | `/bosses/gelum` | Discussion #1(英文评论) |
| `/ja/bosses/gelum`(日文) | `/ja/bosses/gelum` | Discussion #2(日文评论,独立) |
| `/ja/bosses/pyra`(日文,回退英文内容) | `/ja/bosses/pyra` | Discussion #3(独立,日文用户可讨论翻译需求) |

**结论**:pathname mapping 天然产生「不同 locale = 不同评论区」。与「文章正文 fallback 到英文但 UI 是日文」的站点行为自洽 —— 日文用户看到英文正文 + 日文评论框,在日文评论框里用日文讨论,不会被英文评论淹没。这是 feature 不是 bug。

### 4.3 i18n 文案改动(最小:每语言 +1 key)

```json
// src/locales/en.json → shared 段
"shared": {
  ...
  "commentsHeading": "Comments"        // 🆕
}

// src/locales/ja.json → shared 段
"shared": {
  ...
  "commentsHeading": "コメント"         // 🆕
}
```

**为什么只加一个 key**:Giscus 自己的 UI(「写评论」「点赞」「按时间排序」等)由 Giscus 的 `data-lang` 控制,不从站点 JSON 读。站点只需提供一个 H2 标题文案,让评论区与文章页其余区块(Related Articles / 関連記事)在视觉风格上统一。

**不新增 `comments` 顶级段**:没有「加载中」「评论数」「发表」等文案需求(这些都由 Giscus iframe 内部渲染),不需要独立 i18n 段落,污染最小。

### 4.4 暗色同步的边界情况

1. **首次加载时的初始主题**:iframe 静态渲染时 query string 里带 `data-theme` 初始值。但 Astro 静态构建时不知道用户主题(主题切换是客户端 localStorage)。**解决办法**:iframe 初始 `data-theme` 用 `light`,客户端 JS 在 `DOMContentLoaded` 时立即读 `<html>.classList` 发一次 postMessage 纠正。代价:暗色用户可能看到评论区闪一下亮色再变暗(约 200ms)。可接受。

2. **主题切换器不存在的情况**:如果换皮用户删了主题切换器,`<html>` 上永远不会有 `.dark` 变化,observer 永不触发 —— 但首次 `DOMContentLoaded` 的纠正仍会执行,评论 iframe 会用 `light` 主题。合理退化。

3. **Giscus iframe 还未加载时切换主题**:`postMessage` 发给一个还没创建 contentWindow 的 iframe 会被浏览器丢弃。解决办法:iframe 加 `@load` 事件,加载完成后立即发一次当前主题(已包含在 §3.6 的 JS 结构中)。

docs/comments.md 大纲:

## 7. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| Giscus 服务宕机 | 低 | 评论区空白,不影响正文 | iframe 失效只是空白,不报错;正文 + 广告不受影响 |
